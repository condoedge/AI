## REGRESSIONS

### 1. team-info-insider t0: crash, 0.55 → 0.00 (the flagged "min_rows 0 rows" gate)

The gate's "0 rows" is an artifact. The eval harness's last-resort catch (`ConversationEvalRunner:159-168`) caught a TypeError, labelled it `errored_stage=retrieval, errored_step=driver`, and dropped the whole trace (QU, cypher and prompts are empty in the JSON).

**Reconstruction from `laravel.log`, trace 01M3S7XNGS9PBJ59X4HVSMMHM3:**
- **QU:** identical to baseline (data_query / lookup / [Team, User] / possessive).
- **Semantic selection:** identical scores (Team 0.6496, User 0.6019, …, members scope).
- **Validation:** `valid:true`, complexity 15, the same as baseline. Safe_stop, canonicalization and the self-scope gate played no part: the query has no comments or odd whitespace and a single `WHERE t.id = 3`, and it executed.
- **Rows were returned.** `enrichResultsWithEntityActions` returns early on empty data, so reaching the enricher proves the query returned at least one row.
- **The query-generation prompt shrank** from 92,920 to 67,561 bytes. The removed EXAMPLE ENTITIES block included `team_type: 2 (integer)`.

**Cypher, baseline:**
```
RETURN t.name AS team_name, t.contact_email AS team_email, t.contact_phone AS team_phone, t.team_address AS team_address, t.created_at, t.updated_at
```

**Cypher, new:**
```
RETURN t.name AS team_name, t.contact_email AS email, t.contact_phone AS phone, t.team_address AS address, t.team_type AS type, t.created_at, t.updated_at
```

**Root cause:** a latent bug in `src/Services/Response/ResponseEntityEnricher.php:48`:
```php
$entityLabel = $result['_label'] ?? $result['type'] ?? null;   // any column aliased `type` is taken as an entity label
$actions = $this->discovery->getAuthorizedEntityActions($entityLabel, ...); // line 57, strict_types, string param → TypeError on int 2
```
The file has been unchanged since commit c264d22 (2026-06-10). This is the first occurrence in any log. Every query that aliases a column `type` hits this path:
- **An integer value** crashes the turn.
- **A string value** (for example `customer_type AS type` = "unit") silently produces bogus entity action chips.

Two things make it worse:
- **The eval driver calls `enrichExecutionResult` outside any `stage()` trap** (`PipelineEvalDriver.php:~292`, pre-existing in HEAD), so the error escapes and destroys the trace.
- **In AiManager, the Phase-1 Task 1.23 try/catch wraps only `executeWithTrueTotal`**, not the enrichment on the next line. Production therefore falls to `answerQuestion`'s catch-all and shows a canned localized error.

**Responsible change: not a Phase-1 code change. Phase 1 only exposed the bug.**
- The trigger is the LLM newly projecting `team_type AS type`. That is actually what the standard asks for ("that it is a management company (its type)"). Without the crash the answer would likely have scored higher than baseline.
- The prompt reshaping ("example nodes no longer in query prompt", about -25 KB) is the only prompt change on this turn, and the `team_type` description line (1=Self-managed, 2=Manager, 3=Ambassador) is present in both prompts.
- With a single sample, I cannot separate the prompt change from LLM variance. Either way it is a trigger, not the cause.

**Fix:**
- **(a)** In the enricher, use only `_label`, or accept `type` only when `is_string()` and it is a registered entity label. Cast or skip otherwise.
- **(b)** Move `enrichResultsWithEntityActions` inside the Task 1.23 try/catch, or make enrichment failure non-fatal: log it and return the un-enriched rows.
- **(c)** Wrap the driver's `enrichExecutionResult` call in `stage()`, so a failure keeps QU, cypher and prompts in the trace and is blamed on the right step.
- **(d)** Add a unit test with a row `['type' => 2]`.

### 2. team-roster t0: "523 distinct roles", 0.85 → 0.55

**Root cause:** `ResultsDataSection.php:82-88` emits the Phase-1 anchor line whenever `anchor_total` is numeric, even when `anchor_total == total`, meaning there is no fan-out and the line adds nothing. The anchor label comes from the QU target types (`[Team, TeamRole]`), so TeamRole was chosen. The projected subject is `u:User` (`member_name = u.name`), and User is not in the QU types. The LLM repeated "distinct TeamRole" as "523 distinct roles".

**Responsible change:** Phase 1, "true_total = row count + separate anchor_total distinct wording".

**Fix:**
- Emit the line only when `anchor_total < total` (real fan-out).
- Derive the anchor from the RETURN projection (the variable behind the first name-like column) before falling back to the QU types.
- Render a human noun ("members") from the entity config instead of the raw label.
- Keep the old "offer the complete list/export" nudge.

### 3. team-roster t1 Excel: contact info dropped, 0.65 → 0.35

**Root cause:** Phase-1 QU now sees the conversation, so it correctly sets `follow_up_reference:true`. The pre-existing export policy in `AiManager.php:~1688-1720` then makes the *previous* rows authoritative whenever `followUpReference` is true. It discards the current query, which had succeeded (5.8 s execution) and carried the requested `contact_email`, first and last name.

**Responsible change:** Phase 1, "QU receives compact conversation block + export-ask guard". It interacts with the existing "anaphora-suspect" guard.

**Fix:** when the current query ran successfully and its columns are a strict superset of the previous result's columns (the user asked to *add* fields), export `current_result`. Alternatively, have QU emit `export_adds_fields`/requested properties and prefer the current result when present. Either way, never report "Fields included" without also saying which requested fields were not included.
