## Remaining regressions vs BASELINE

### 1. ambiguous t1: 0.75 → 0.35 (-0.40), noise in a known family
- **Root cause:** homonym rows (same `unit_name`, different `union_name`) are collapsed at composition, which is nondeterministic. Balance t0 does the same in all three runs. The prompt is byte-identical except for the previous-turn data, so no Task 1.27 change is responsible.
- **Suggested fix:** add a deterministic homonym rule, not an LLM hope.
  - In `ResultsDataSection`, when two or more rows share the display-name column and differ in a disambiguation column, emit an explicit line. For example: "These 3 rows are DIFFERENT units named '310' in 3 unions — report each with its union; never answer in the singular."
  - Suppress single-entity links (`Unit/159`) when homonyms exist, or emit one link per row.
  - Optionally add a post-composition lint that counts distinct disambiguation values mentioned against the rows.

### 2. team-info t0: 0.55 → 0.50 (-0.05), residual gap rather than a code regression
- **Root cause:** enum values reach composition raw. `team_type` meanings (1=Self-managed, 2=Manager, 3=Ambassador) exist only in the query-generation schema, not in the response prompt, so the model prints "Team Type 2". The member count is also absent, because the cypher selects only Team properties.
- **Suggested fix:**
  - Decode enum columns in the result formatter (or pass the value labels from entity config into the results section).
  - For a "my team" overview, have the query generator add `count { (u:User) WHERE u.current_team_id = t.id }` (or `size(...)`).
  - Keep the doors list (members / unions / finances / meetings) in the next-step guidance.
