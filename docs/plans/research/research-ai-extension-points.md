## 0. The five findings that matter most

1. **Two natural takeover points, both reuse the persistence path.** (a) `AskQuestionUseCase::runTurn` line 247 (`AI::answerQuestion(...)`) is the only place a turn is dispatched; swapping that call for an orchestrator that returns the same response array keeps the security gate (step 0), trace, audience stamp, user-message persistence, context write and assistant-message persistence for free. (b) Inside `AiManager::runAnswerPipeline` a new early branch (before `understanding`, line 917, or right after QU, before page narration, line 971) follows the existing branch convention. Use-case level is reachable by ai-eval (`PipelineEvalDriver` calls `AskQuestionUseCase`).
2. **The package has NO state primitive for a task.** What survives between turns is: `ai_conversations.context_snapshot` (JSON, written once per turn by `ConversationContextManager::recordResponse`, only RAG-ish keys), `ai_conversations.metadata` (JSON, only `pinned` used), the last 10 messages (`max_history_messages`) with answers cut to 800 chars, and per-message `metadata`. A task needs its own persisted state (draft, step, counters, status, version). Nothing locks a conversation: two concurrent turns can interleave (no `lockForUpdate` / `Cache::lock` in the chat path).
3. **The action system already is the write path, and it is approval-gated, but it has gaps for a rich confirm.** `AiActionInterface` (`mutates()` true -> `ActionDispatcher::defer` mints a signed `PendingActionToken`; `approve()` re-authorizes, single-use nonce, TTL 900 s). Gaps: the approval card text is hard-coded `'This will {label}. Confirm?'` (`ActionDispatcher.php:172`), so it cannot show a campaign summary; there is **no audit row anywhere** for proposals/approvals/executions (the actions review lists it as undone D2); the token is bound to user+action+input only, not team, message or draft version (review A4 open); the post-approval result is `$result->renderable` which for a mutation is an array, not a Kompo element (`MessagesQuery.php:474-` **OPEN**: verify what the panel shows).
4. **LLM plumbing is ready for a structured, schema-bound orchestrator brain.** `LlmResolver::forRole()` + `chatJson(..., ['json_schema' => ['name','schema']])` (strict on OpenAI; ignored by Anthropic provider, which has no `jsonSchemaOptions`), usage reporting via `TokenUsage::report`, prompts to observers via `promptBuilt`. Native tool-calling was **deleted** on 2026-10-01 (`docs/plans/2026-10-01-actions-review.md` progress log), so the orchestrator should be "one JSON-schema call per step, code executes", not a tool loop.
5. **Chat UI is message-shaped, not widget-shaped.** A bubble = markdown text + `metadata.invocations` chips (re-dispatched with fresh authorize at every render) + `response_data` (table/metric/list) + follow-up question chips that fill the composer and click send (`SuggestionSubmit::fillAndSendJs`). There is no in-bubble form/input component, no "summary card" element, and no direct "post an answer" endpoint other than the composer. A choice chip = a typed message (goes through gate + turn pipeline). Rich widgets need a new renderer hook (`MessageBubbleRenderer::assistantBubble`, line 123) or a Kompo form rendered as an invocation element.

### 1.4 Where a "task mode" could take a turn, with trade-offs
| Option | Where | Pros | Cons |
|---|---|---|---|
| A. Use case, before `AI::answerQuestion` | `AskQuestionUseCase.php:247` (after user message persisted at 220, observer + audience ready) | Gate, trace, user/assistant persistence, audience stamp, error mapping all reused; no QU call; reachable by eval; does not touch AiManager (5.8k lines) | Skips `admitTurn` rate limit (must call `QueryExecutor::admit` or its own limiter); `recordResponse` still runs (harmless: preserve-on-empty at `ConversationContextManager.php:139-167`, but `last_answer_summary`/`last_query_type` are overwritten at 124-130, 188) |
| B. AiManager, before `understanding` | `AiManager.php:~910`, after `admitTurn` | Gets rate-limit admission and `PipelineObserverScope`; same return shape | Adds to the monolith; AiManager has no conversation access (only `options['conversation_id']`, `conversation_context`), so the orchestrator must load the conversation itself |
| C. AiManager, after QU | `AiManager.php:~971` | Can use QU language/intent signals; sits with the other branches | Pays a QU call every task turn; QU free text of a task answer ("yes, March 3") is meaningless to QU; QU output is language-detection only (`qu->language`) |
| D. UI-level (ChatMessageForm/presenter) | `ChatPresenter::handleSend` | Cleanest separation | Loses use-case guarantees; regenerate/edit/eval paths bypass it |

**Staying in a task across turns:** a per-turn precondition read, not a model judgment: "does this conversation have an active task row/state?" (structural, same philosophy as `ClarityChecker::blockedBy`, `src/Services/Understanding/ClarityChecker.php:178`, whose own doc states that gates are structural, not word lists). The use case already holds the `AiConversation`, so a state lookup keyed by `conversation_id` fits at A.

**Starting a task** (all three are compatible with "code decides, model narrates"):
- Explicit: a code-attached chip/button on an answer or the welcome screen. `ActionAttacher` already attaches action invocations; a `start_task` generic action (class in `ai.actions`, `config/ai.php:1880`) whose `handle` returns a "begin" intent.
- A small dedicated classifier call like `ClarityChecker`/`NavigationPages` (own role in `ai.llm_roles`, strict schema, `TokenUsage::report`, fails closed to "no task").
- QU extension: ruled out above (snapshot + cassette guards).
**Leaving** a task: explicit cancel chip, completion, TTL expiry, or the classifier saying the message is off-task.

### 1.5 Message-level consequences of the existing flows
- Regenerate: `RegenerateAnswerUseCase::truncateTrailingMessages` deletes every message after the target user message (`RegenerateAnswerUseCase.php`, `execute` -> truncate -> `askQuestionUseCase->regenerate`). Edit-and-regenerate does the same. Task state kept in conversation-level JSON will NOT roll back with the deleted messages; state kept per message (e.g. `metadata.task`) would. Decide whether a task turn may be regenerated (a write step must never be replayed). **OPEN design choice.**
- Feedback and the pin toggle do whole-JSON read-modify-write on `metadata` (`src/Kompo/Support/ConversationActions.php:38-40, 62-67`), so a task state in `ai_conversations.metadata` would race with them. A separate table or its own column avoids this.
- The conversation soft limit banner at 30 messages (`MessagesQuery.php:215`, `ConversationLimitBanner.php:40`) never blocks sending; it will fire during long tasks (advisory only).

### 2.2 What survives between turns
- **Snapshot, written once per turn after the pipeline** (`ConversationContextManager::recordResponse`, `src/Services/Context/ConversationContextManager.php:53-193`): `focused_entity`, `mentioned_entities` (cap 10), `last_relationships`, `last_answer_summary` (500 chars), `updated_at`; only when rows were produced: `last_cypher_query`, `last_generated_cypher`, `last_anchor_label`, `last_cypher_parameters` (raw PII by design, `config/ai.php:607-610`), `last_result_count`, `last_result_sample` (first 10 rows, digest keeps all), `focused_entity_filter`, `last_entity_types`, `last_subject`; plus `last_referenced_files`, `last_query_type`.
- **Read back** by `buildPromptContext` (251-278) as `conversation_context` = those keys + `recent_exchanges` (formatted by 286-304: role, user text, assistant answer cut to `ai.chat.history_answer_chars`=800). History depth is `ai.chat.max_history_messages`=10 (`config/ai.php:1770`). Only `user`/`assistant` roles are meaningfully formatted (a `system` role message would carry null question and answer).
- Message `metadata` keys the code already uses: `referenced_files`, `error`, `regenerated`, `audience`, `invocations`, `resolved_invocations` (fingerprint -> 'approved', stamped by `MessagesQuery::markInvocationApproved`, `MessagesQuery.php:534`), `export_document_markdown/rows/headers`, `cypher_parameters`, `trace` (<= `ai.trace.max_bytes`), `feedback` ('positive'|'negative'). Free keys are fine (the `metadata` column is a plain JSON blob).
- Per-message `context_used` stores the conversation context that fed the turn (useful for audit and for debugging a task step).
- Ownership: all chat UI lookups scope to `user_id = auth()->id()` (`ChatMessageForm.php:64`, `MessagesQuery::created`, `ConversationActions::ownedConversation`); `AiConversationPolicy::view` also lets team members see a conversation (`src/Policies/AiConversationPolicy.php`), `delete` is owner only.
- No concurrency control on a conversation (only `DocumentMapBuilder` uses `Cache::lock`, and `ModelMethodMutationAction::lockForWrite` locks the *target* row). A task orchestrator must provide its own per-task lock or optimistic version.

### 2.3 Implications for task state (facts, not decisions)
- Cheapest vehicle already in schema: a key inside `ai_conversations.context_snapshot` or `metadata`. Both are shared read-modify-write JSON blobs with other writers (see 2.2, 1.5), the snapshot is rewritten on every turn (merge preserves unknown keys, `array_merge` at 169), and `buildPromptContext` returns only a whitelist, so extra keys do not leak into prompts.
- A dedicated table/column (new migration; the package already ships migrations via `loadMigrationsFrom`, `AiServiceProvider.php:801`) avoids races with pin/feedback writes and carries versioning and audit better.
- Resume UX: `ConversationResumeBuilder` (`src/Services/Chat/ConversationResumeBuilder.php:31`) builds a copy-paste resume from the snapshot only; a task would be invisible to it.

### 4.3 Observers, trace, usage

### 4.4 Prompt building and tests

## 7. Security and limits primitives

- **Auth to the user**: every chat turn requires a user (`ChatSecurityGuard::assertSafe` throws `InvalidArgumentException` without one unless `allowAnonymous`, `ChatSecurityGuard.php:39-46`); the UI scopes conversations by `user_id` (2.2). `options['user']` carries the actor into everything downstream (e.g. `AiManager.php:1081`).
- **Prompt-injection gate**: `InputSanitizer::analyze` run on every typed message (`ChatSecurityGuard.php:49-58`; regex patterns, `addPattern` extensible, `src/Services/Security/InputSanitizer.php:62-157`). Decline-and-continue; also re-run by regenerate. Applies to task answers too; a false positive on a free-text answer would refuse that step (no persistence).
- **`AiAuthAdapterInterface`** (`src/Contracts/AiAuthAdapterInterface.php`): READ scoping only (teams with permission per entity, global count, enabled, permissions-exist). It scopes graph queries (`AiSecurityService`, `TeamPathResolver`), not writes. Coolecto's adapter returns the user's `current_team_id` (`host:app/Ai/AiAuthAdapter.php`). **It provides no write authorization**; write authorization lives in `AiActionInterface::authorize` (host policies/gates).
- **Audiences** (`Support/Audiences.php`): `of($user)`, `documents($user)` (document access filter), `prompt($user)`/`promptBlock` (role text with `{role}`), `insiderVoice`, `exampleQuestions`; resolver precedence in Coolecto: scanner > participant > buyer > supplier > organiser + role (`host:app/Ai/AudienceResolver.php`). The audience key/role are stamped on the trace stage and on message `metadata.audience` (`AskQuestionUseCase.php:232-237, 271`). An audience map entry is a free array (the package reads only `documents`, `insider_voice`, `prompt`, `example_questions`), so a `tasks` list on it would be unread config the package could own.
- **Rate limits and admission**: `ai.rate_limits` (`config/ai.php:739-744`): `queries_per_minute` 30 per user (scope `u:<id>`, `QueryExecutor::rateLimitScope`, ~389), `global_queries_per_minute` 300, `max_wait_seconds` 20, `llm_requests_per_minute` 60 (`Resilience/RateLimiter.php:125-131` `forLlm()`). Verified: `forLlm()` is used only by `QueryGenerator.php:103`, so the per-minute LLM limit does NOT cover QU, composition, clarity, navigation or any new orchestrator call. The query limiter is charged only by `admitTurn` and query executions; a task turn at the use-case level is charged nothing today.
- **Circuit breaker + retry** for every LLM call (`ai.resilience.llm`, `config/ai.php:759-773`); breaker name `llm` shared; `LlmResolver::isolated` for separate breakers.
- **Write-safety defaults**: the pipeline options a chat turn may set exclude `allow_write`/`read_only` (`AskQuestionUseCase.php:47`); `ai.query_generation.allow_write_operations` default false (`config/ai.php:646`) concerns generated Cypher (the graph is a read model; domain writes go through the host's Eloquent code via actions).
- **Untrusted text handling**: spotlight fences for question/documents/data in sections (`BaseResponseSection::spotlight`, `BasePromptSection` same), `UntrustedLabel` for one-line labels, `NarrativeLinkFilter` stripping model-written links, `PiiMasker` (response side), `TraceRedactor` for persisted cypher/errors. A user's free text going into an orchestrator prompt needs the same spotlight treatment (helpers are protected methods on section base classes, not a standalone utility: **OPEN** whether to extract one).
- **Admin / audit views**: gate `viewAiConversations` (denied unless the host defines it, `AiServiceProvider.php:789-797`; `ConversationInsights::ABILITY` `ConversationInsights.php:37`); route `ai.admin.conversations` (`routes/web.php`, config `ai.admin.*`); Kompo pages `AiConversationsAdminPage`, `AdminConversationsTable`, `AdminFeedbackTable`, `AdminTranscriptModal`; `ConversationInsights` (`kpis`, `feedbackQuery`, `conversationsQuery`, `transcript($uuid)` line 297, `traceSummary` 333). `ConversationInsights::transcript` (297-318) loads id, role, content, metadata, execution_time_ms for every message of a visible conversation; `AdminTranscriptModal::messageBlock` (69-92) displays content + feedback + trace summary only, no invocations/approvals/task state (display would need extending; the data is already loaded).
- **Policies**: `AiConversationPolicy` (`view`: owner or same team; `sendMessage` same; `delete`: owner), registered in `boot` (`AiServiceProvider.php:789`).

## 8. Gaps a task orchestrator would hit (list, no design)

1. State: no task store, no versioning, no per-conversation lock, regenerate/edit truncation semantics (sections 1.5, 2.2).
2. A "create" shaped mutation: `ModelMethodMutationAction` needs an existing row id; a create requires a bespoke `AiActionInterface` (class in `ai.actions`, built with `new`, no ctor args).
3. Approval card shows only the action label; no summary/diff, no server-side cancel, token not bound to a draft version or team (review A4); no audit rows; post-approval renderable shape unclear (3.3).
4. Starting a task: no code path from "I want to create a campaign" to a task. QU intents are closed and prompt-guarded; the existing nav button `new_campaign` (`host:config/ai.php` navigation) is a link to the manual form.
5. Rate limiting/admission for non-pipeline turns (1.4); the LLM-per-minute limiter covers query generation only (7).
6. Observer vocabulary: a task needs its own stages and trace data; `MessageTraceObserver::redactStageData` whitelists stage data (4.3, **OPEN**).
7. Admin transcript displays no task/approval state (7); the metadata is already loaded, only rendering is missing.
8. Structured user input: chips = typed text; no structured value channel or in-bubble form (6.2).
9. Streaming/timeouts: turns are one synchronous request (6.1).
10. Guards on existing behaviour: PromptSnapshotTest and the ai-eval cassette require every non-task turn to remain byte-identical; any hook must be inert when unconfigured (CondoEdge and SISC share the package by symlink).

## 9. Open questions (for the design)

- Where task state lives (new table vs snapshot/metadata) and its relation to regenerate/edit truncation.
- Use-case takeover (A) vs AiManager branch (B): who owns rate-limit admission and observer stages for a task turn.
- How a task is started (explicit chip/action vs small classifier role) and ended.
- Whether the orchestrator reuses `AiActionInterface` + `ActionDispatcher` for the final write (gets signed token, nonce, re-authorize, `resolved_invocations`) or introduces its own confirm path; either way it needs an audit table and a richer card.
- Host-supplied domain: nothing in the package today lets a host register "task definitions" (steps, schema, validators, creator). The closest conventions are `ai.actions` class lists, `ai.audiences.resolver`, `[Class, method]` gates, and `ai.domain.*` slots; a contract + config registry fits (convention 1, 2, 3 above).
- PII/identifying-field masking for task prompts outside `PipelineContext` (4.4).
- Per-task LLM role (`ai.llm_roles.task_orchestrator`) and Anthropic's lack of strict schemas (4.1).
