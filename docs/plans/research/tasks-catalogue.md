# Coco tasks catalogue: every write an organiser (and a supplier) performs in Coolecto

Read-only research for the next plan (2026-10-25). This file states facts, not a plan. Paths are relative to
`C:\Users\jkend\Documents\Projects\kompo\ActiviteDeFinancement` unless they start with `ai/` (the condoedge/ai package).
Companion file: `campaign-go-live.md`.

**Method.**
- Every help article was listed: `resources/ai-help/aide/organisateur` 328, `fournisseur` 54, `participant` 27,
  `acheteur` 57.
- The organiser and supplier articles were read area by area. The code behind each write was traced: route → Kompo komponent →
  write method → service/model, with the authorization, validation and side effects found in code.
- Usage numbers are read-only aggregates from the local `financement` DB (§3). No personal value was read or printed.
- Buyer (`acheteur`) and participant actions are self-service on public pages (pay, register, set a personal goal). They are
  out of scope here. They are listed only in §5.
- Unverified points are marked **OPEN**. "IDOR candidate" means: read in code, not exploited.

**Column legend** (the tables in §6):
- *risk*:
  - `money`: amounts, prices, fees, profit split.
  - `legal`: tax receipts, raffle licence/draw, supplier terms, consent.
  - `outward`: sends to people outside the team, or changes a live public page.
  - `destructive`: deletes, or changes something irreversibly.
  - `internal`: reversible, internal only.
- *fit* (the existing orchestrator does one draft of typed fields → one confirmed write):
  - `yes`: fits that shape.
  - `multi`: several new records in one go.
  - `bulk`: acts on many existing rows.
  - `upload`: needs a file.
  - `provider`: Stripe, a bank or an external provider.
  - `iterative`: needs live design or feedback.
  - `no`: other, the reason is given.
- *size*:
  - `S`: reuses the `CampaignSettingsWriter` pattern; under a day.
  - `M`: new writer plus rules extraction.
  - `L`: new domain service, several records, edge cases.
- *reuse*: an existing service or static rule a task could call.

## 2. Cross-cutting facts that decide every task

1. **The UI is the only role check on most writes.**
   - Kompo AJAX writes go to `/_kompo` with the `web` middleware only (`vendor/kompo/kompo/routes/web.php`). Route groups
     run on page load, not on the write.
   - `my-campaign/*` pages are `['auth', 'profile:team|supplier']` (`routes/web.php:275`) with no role. `org.*` pages are
     `auth` only (`routes/kompo/teams.php:5`). `role:supplier` only checks that the team is a supplier
     (`app/Http/Middleware/RoleMiddleware.php:27`).
   - Result: a Member ("Membre", `basic`) can change fees, profit share and receipts, and delete a campaign.
     - The settings link is not role-gated (`app/Kompo/Menus/DashboardSidebar.php:329`).
     - `CampaignPolicy::delete` checks the team only.
     - Every setup-card modal is open to Members.
     - Products, dates and inscription courses are open to Members.
     - Participants are editor-only in the sidebar (`:336`) but not in the child tables' methods.
   - Real server-side role checks exist only for:
     - member management (`TeamPolicy`, chief admin);
     - manual payment (`CampaignOrderingTrait.php:156`);
     - refund and link-to-participant (`OrderPolicy.php:63-75`);
     - Inscriptions go-live and setup (`isEditor`);
     - the network catalogue cards (`authorizeBoot`, manager/agent);
     - the onboarding-wording forms (supplier);
     - `survey-delete` (`web.php:33`, manager).
   - A task cannot "re-check the same authorization as the UI": for most actions the UI's rule is a hidden button. Each task
     needs a gate of its own. `CreateCampaignTask` uses `NavigationGates::campaignCreator`; others exist: `editorOnCampaign`,
     `managerOnCampaign`, `manager`.
2. **Ids from the client are often not scoped.** Many write methods load a record by an id sent with the AJAX call, with no
   team or campaign check (IDOR candidates). They are listed in each area's notes:
   - invitations, tax receipts, mark delivered, change date, replace product, scanners/terminals, encan bids;
   - variants, vouchers, prizes, dates, groups, recipients, communications, contacts, sponsors;
   - supplier deliveries and products, inscription dates/places/students, form sections and questions.

   A task must load every record through `currentTeamId()` / `currentCampaign()` itself and must not call these methods as
   they are.
3. **Security findings to fix before any task exposes the same paths** (from code reading, not reproduced):
   - `RoleManagementModal` accepts role `admin` (rules `:100`), which reaches `users.current_role` → platform admin through
     `isAdmin()` (O5).
   - `qr-code-check` (`web.php:62`) has no middleware: it marks tickets scanned and returns the buyer's e-mail (O66).
   - `InviteToBecomeOwnerModal` takes a team id from the payload (O33).
   - The "let managers manage the bank account" toggle has no owner check (O16).
   - `SupplierPaymentSettingsForm::afterSave` (`:15`) wipes `pay_fixed_fees` on the supplier and on every client campaign
     each time it is saved (F24).
   - `ShopifyController.php:47-56` can log a browser in as the supplier's user when the shop e-mail matches (F32).
   - Signed links with no login and no expiry:
     - `client.handle-campaign-end` (extend, close, send orders to the supplier);
     - `approval-request/{id}` (a decision can be flipped later);
     - scanner invitations.
   - `switch.campaign` follows `redirect_to` from the request (open redirect).
4. **Few writes are transactional.**
   - Only `CopyMainCampaignModal::handle` and a few services (`P2pService::upsertP2PRecipient`, `CampaignSettingsWriter::write`)
     use a transaction.
   - Copies, the Excel "replace" flows, the activity writer and form imports save in several steps.
   - The orchestrator's own `DB::transaction` around `execute()` (`ai/src/Services/Tasks/TaskOrchestrator.php:645`) covers a
     task. A task must not call code that dispatches mail or jobs inside that transaction without care.
5. **Static rules exist today for 8 settings cards only**: `StepCampaignDates::datesRules`, `StepCampaignShowGoal::goalRules`,
   `StepCampaignDonation::donationRules`, `StepCampaignCoverFees::coverFeesRules`, `StepReceiptsAndTaxReceipts::receiptsRules`,
   `StepCampaignContacts::contactRules`, `StepCampaignReason::reasonRules`, `StepCampaignLeaderboard::leaderboardRules`. Other
   reusable code:
   - `Campaign::drawLicenceRule`
   - `TeamInvitationForm::invitationRules`
   - `ImportRowCustomersImport::makeValidator`
   - `App\Services\Inscriptions\ActivityWriter` (tested)
   - `P2pService::upsertP2PRecipient`
   - `Deliverable::addAllProductsOfSupplier` / `createOrUpdateEquivalentProduct`
   - `CampaignCopyTrait`, `CommunicationSender`, `ResendOrderEmail` rules, `CampaignGoLiveService::goLive`,
     `ApprovalRequest::approveCampaign`

   About 20 more settings cards save plain columns with trivial `rules()`: adding each to `CampaignSettingsWriter` is size S
   (part S notes).
6. **Known gaps in `CampaignSettingsWriter`.**
   - Raffle dates always fail: `datesRules` requires the draw fields, which the writer never supplies. The writer also skips
     the card's lock and draw-after-end checks (`StepCampaignDates.php:40,44`).
   - `datesRules` validates `max_amount_prize`, but the input is `max_prize_amount`.
   - Suppliers and Inscriptions use other date cards, so `dates()` is refused for them.
   - Fields outside its list are dropped silently by `Arr::only` (`CampaignSettingsWriter.php:245`): contact phone,
     participant/group goals, donation without purchase, round-up, forced cover fees.
7. **Implicit writes on GET.**
   - Any full-page GET can put the current campaign online (`EnableCampaignIfReadyMiddleware`), so a task that completes the
     last required card publishes the campaign (`campaign-go-live.md` §1).
   - Opening `campaign.survey` creates the Survey row and can put the campaign online.
   - Raffle draws run in `created()` of their modal on a GET.
   - Opening an internal unsubscribe form unsubscribes the contact.
   - Saving a webhook rotates its secret.
8. **The orchestrator's `list` field is a list of enum options** (`ai/src/DTOs/Tasks/TaskField.php`, `hasValidType`). There is
   no list of records: "3 products with name and price", "4 dates", "5 groups with a delegate". A `multi` task needs a new
   field type in the package or one task run per record.
9. **Code and help disagree** (fix one or the other before Coco cites them):
   - The AI e-mail sequence creates e-mails **enabled** (`ExecuteCommunicationPlanJob.php:145`), but the article says they
     arrive disabled. Copy and duplicate also keep `enabled`.
   - Approving from the « Demandes » card e-mails no one.
   - « Tirer ce prix » e-mails no one, and « Tirer tous les prix » e-mails every draw again.
   - « Renvoyer le reçu » re-sends the tax receipt and does not regenerate it.
   - "Participant added" e-mails ignore the communication's `enabled` switch (`Campaign::sendCommunicationsFor`,
     `Campaign.php:2416`).
   - The participant Excel replace stops halfway without a message.

#### Area notes

- No card on the settings page has any role or policy check: every write rests on `auth` + `profile:team|supplier` (web.php:275) and the campaign bound at boot from `currentCampaignId()` (CampaignPageSettings.php:19). The sidebar link is not role-gated (DashboardSidebar.php:329), so a "Membre" (basic) can change fees, profit share, receipts, or delete the campaign (only CampaignPolicy::delete:71, a team check, applies).
- Only 8 cards expose static rules (dates, goal, donation, coverFees, receipts, contact, reason, leaderboard), plus the reusable `Campaign::drawLicenceRule()` (Campaign.php:2940). About 20 other cards are flat columns with no or trivial `rules()` and no hooks, so adding them to `CampaignSettingsWriter` is cheap (S): name, buttons, social share, donors list, needs-address, invitation code, ICS, order bump, terminal, membership, encan, P2P text cards, groups, P2P goals, profit share, participants message, invoice comment, max-days-before, delivery type.
- Writer coverage is partial on 4 covered cards: contact (no phone), goal (no participant/group goals, total-only), donation (no donation-without-purchase, round-up), cover fees (no forced). The "card is offered" check passes, but those fields are dropped silently by `Arr::only` (CampaignSettingsWriter.php:245).
- Bug: on a raffle, `CampaignSettingsWriter::dates()` can never pass. `datesRules` requires drawing_datetime/venue_address/minimum_age (StepCampaignDates.php:233), and the writer never puts those in its validation data (FIELDS :33, validationData :199). Also, `datesRules` validates `max_amount_prize` while the input is `max_prize_amount`.
- The writer also skips two server checks: the raffle "locked info" check (StepCampaignDates.php:40) and the draw-after-end check (:44). Any writer extension for raffles must add them. The "allow manual draw date" toggle (:216) already saves with no lock check.
- For supplier users and inscriptions, the dates card is a different class (StepCampaignDatesSupplier, SetupAudienceStep), so the writer's offered-card check refuses `dates()` for them.
- Cards with real side effects need more than column writes. Dates trigger communication rescheduling (CampaignSetAndHandleDatesTrait.php:125). The participants-list choice can delete prepared envois (SaveRecipientSetting.php:38) and needs its confirm modal. The SMS end reminder queues an SMS to bidders (Campaign.php:3118). Event dates create reservations and envois. The cover image generates a social banner. Template propagates to sub-campaigns. Delete cascades widely.
- Personal data / minors: leaderboard (S17) and the participant message (S56) publish to or reach participants, who are often children. S43 and S65 decide whether child birth date, school, level, gender, phone and address are collected. Donors list (S27) publishes donor names and amounts. These should be legal/consent rows in any task summary.
- Possible IDOR spots (code read only, not exploited; OPEN): `CampaignExperienceTab::addNewActivityToCampaign` (any campaign id), `LinkedCampaignExperiencesQuery::toggleMandatoryPurchase` (any experience id), the level/link/date modals opened by selfUpdate ids (saving them keeps their record), `CampaignLinkForm.linked_campaign_id`, `CampaignPhotoForm::pickCampaignPhoto` photo id, and tag ids in S55.
- Multi-record cards (P2P team types with fees, levels, challenges, event dates, campaign links) fit a list field, but they have no service: each is a Kompo form per row. P2P pricing is the only one with money on every row.
- Upload-only actions: cover image (S22), custom logo (S24). The form editor (S48 after creation) and the P2P participant form (S44) are iterative and live on other pages.
- Odd facts: `opening_balance` is write-only (not read anywhere in app/). The SMS reminder on/off toggle is not stored, and it is OPEN whether switching it off cancels the job. `StepCampaignVenueDates` has no submit on the settings page. `VenueDatesQuery::toggleCampaignDate` is unwired. Rendering the P2P form card creates a Survey row.

#### Area notes

- No role check on any setup-card write: every band modal is reachable by any team user who sees the dashboard (Member included; scanners are routed away). Only `NewOnboardingCard::goLive` and `SetupShareStep` check `isEditor`, and the bank card gates by `canManageBankAccount` in the UI only (`BankInfoStep.php:85`); `getBankForm` itself has no check.
- Going live is a side effect: `EnableCampaignIfReadyMiddleware` (any full GET) and `DashboardView::created` call `CampaignGoLiveService::enableIfReady`. A task that completes the last required card publishes the campaign on the user's next page view; the confirmation summary must say so.
- Reusable now: `CampaignSettingsWriter` (dates, goal, donation, reason) and the static rule methods; `CampaignCopyTrait` (`createCampaignCopy`, `createCampaignCopyWithRelations`, `copySupplierTemplate`); `CampaignGoLiveService::goLive`; `Campaign::lockDates`; `confirmClosingProductDeliveryCampaign`; `ApprovalRequest::approveCampaign`. Copy logic for L1/L3 lives in Kompo `handle()` methods and must be extracted first.
- `CampaignSettingsWriter::dates()` lacks the tirage guards of `StepCampaignDates::beforeSave` (locked info, draw after end) and the tirage fields; extending dates on a raffle via the writer would skip the lock. `setAllowDrawDateToBeManually` also writes after the lock.
- Copies within an agent network cross teams: `getCopiableCampaigns` adds every campaign under the agent (`Team.php:557`), so a team can copy a sibling team's participant list (MINORS) and triggers LLM rewrites of the copied e-mails.
- Two lifecycle pages run on signed URLs without auth or expiry: `client.handle-campaign-end` (extend dates, close campaign, send orders to supplier) and `approval-request/{id}` (approve/refuse, no pending check, can re-flip a decision). Whoever holds the e-mail link can act.
- `AllCampaignsTable::toggleVisibilityCampaign` and `setFeaturedCampaign` take the campaign id from the browser without team scoping (verify IDOR); `switch.campaign` redirects to `redirect_to` from the request.
- Campaign delete is a hard delete with a long cascade (recipients, donors, communications, products...). Guards: CampaignPolicy (same team, no role) + no paid orders/landing orders/delivery amounts. Not a good task candidate, or staff-only.
- Approving from the Requests page sends no e-mail to the requester, while the article says one is sent; only the signed-link path (`changeStatus`) notifies. There is no refuse button on the Requests page.
- Several "done" flags are acknowledgements (welcome_completed_at, communications_reviewed_at, delivery_choice_made, no_communications, onboarding_without_groups); a task should not set them without showing the user what they acknowledge.
- `travel_funds_go_to` is stored but read nowhere in code (OPEN: manual routing by staff), and supplier terms acceptance (L5) is validated but not persisted for audit.
- `CopyMainCampaignModal::handle` is the only copy in a DB transaction; L1, L4, L5 and L7 save in several steps and can leave half-made campaigns on error.

A single `ProductWriter` that pulls its rules (PF:433) and beforeSave/afterSave (PF:62-145) into static methods would cover P1-P7, P16-P18, P22, P25, P28-P34.
- Supplier locks are enforced server-side only for name/introduction/description (PF:84-90), price range (DLV:221) and cost (DLV:239). Images and variants are blocked in the UI only. `TeamLockGuard::assertCanSaveProduct` only applies to product-sale campaigns of reserved teams.
- `locked_dates_and_prices` (raffle): it blocks new products (PF:47), price and number changes (PF:92), deletion (PM:779) and prize edits (DrawingPrizeForm.php:34). The "Duplicate" button bypasses it (P6).
- Live-campaign effects: a price change applies to the next orders only. Cost, tax-receipt amount, "do not add to receipt" and taxable amount are read from the product when they are used (OrderDetail.php:400, :822-839), so a change rewrites profit and receipt figures for past sales. Changing a ticket's linked dates deletes or creates QR reservations of tickets already sold (PM:909).
- Possible IDORs (ids taken from the request without a team check; to verify before any task reuses these paths): variant form (ProductVariantsMatrix.php:26), voucher edit (CampaignVouchers.php:84), date toggle and date edit (CampaignDatesQuery.php:85/:103, VenueDatesQuery.php:80), prize edit (DrawingPrizeQuery.php:70), prize delete (`Prize::deletable` ignores the team, Prize.php:50), sponsor and category edit (beforeSave rewrites team_id), and cancelling a recurring donation (TeamRecurringDonationsTable.php:76).
- Probably broken for organisers: deleting a ProductVoucher (P54) and a Dimension (P14). Neither model has `deletable()` or a policy, so the Kompo delete returns 403 for non-admins.
- Outward side effects found: the supplier first-product e-mail (PM:894), the gift certificate e-mail (Voucher.php:405), donor e-mails on a date change (CampaignDateChangeForm.php:53), the venue request e-mail to staff, and Stripe checkout-session expiry on product delete (PM:794). There are no queue jobs beyond the queued gift-certificate mail.
- Deleting a product deletes unpaid order lines, reservations and auction bids (PM:796-808). Hiding is the safe route, and a task should offer "hide" by default.
- Best first tasks (yes, S): change price (P2), hide/unhide (P7), add a supplier product or all of them (P19/P20, already-used service), create vouchers (P51), create and send gift certificates (P57/P58, rules already inline), and the settings toggles P23/P46/P48/P61/P62 through the CampaignSettingsWriter pattern.
- Avoid or defer: the variants matrix (P13/P15, iterative grid), image uploads (P5), Stripe subscription actions (P26/P27), and ticket date relinking with sales (P31) until there is a warning step.
- Sort `products_sort_by` is stored unvalidated and passed to `orderBy` (PM:694). A bad value breaks the product list, so a task must write only values from `orderablesOptions()`.

#### Area notes

- No role check at all on `campaign.page.inscriptions` (CampaignPageInscriptions.php:13) or on its tabs. A Member can add, edit, price, duplicate, paste and hide courses, edit places and dates, edit or delete students, and move registrants. The `isEditor` check on `campaign.inscription-setup` (InscriptionSetupPage.php:73, SetupActivitiesStep.php:16, SetupShareStep.php:32) covers only the setup page: the same `InscriptionActivitiesList` is mounted without it on the Inscriptions page.
- `App\Services\Inscriptions\ActivityWriter` is the reusable core for activities: `saveGroups`, `saveGiftValues`, `duplicate`, `createFromLines` and `blocksOf`, already covered by tests/Feature/Campaigns/ActivitySetupTest.php. The missing piece is the product-level fields and `rules()`, which live in InscriptionActivityForm.php:74/:723 and should become a static (the `datesRules` pattern). `saveGroups` treats a missing block as "remove the group", so a one-group edit must resend every block from `blocksOf()`.
- Nothing in this area runs in a DB transaction: Kompo Form saves, ActivityWriter, the paste list and the survey import. A task's confirmed write should wrap its own transaction.
- Destructive surprise (OPEN, reproduce): on a registration's invitation share step, "Supprimer les anciens participants et utiliser cette liste" (RecipientsImportErrorsQuery.php:156) query-deletes all campaign groups, and a registration's groups are its course groups. It also deletes all registered children's records.
- Unscoped ids from AJAX params (Kompo method args are client-supplied, unlike props): InscriptionDateForm.php:73 deleteDate, InscriptionDatesPanel.php:71/:78, InscriptionLocationsQuery.php:67, InscriptionStudentsQuery.php:140, CampaignGroupsQuery.php:133/:140, InstallmentPlansTable.php:66, CampaignOrdersTransactions.php:224, ProductChangeOrderDetailsQuery.php:68, SurveyPollSectionsList.php:150, EditPollForm.php:76, and ImportSurveyPollsForm (route id + campaign_id). Each one could reach another team's row. Scope them before a task reuses any of these entry points.
- Forms: only "delete the whole form" is manager-only (web.php:33). Every other editor write relies on SurveyPolicy::update (same team, any role) checked once by the parent page (surveys/.../SurveyFormPage.php:14). `surveyStillEditable()` always returns true, so deleting a question, deleting a section or importing questions silently deletes answers already collected.
- The form editor is iterative by nature (sections → questions → choices → conditions/arrows, with a live plan and branching-issue check). Good one-shot candidates in it: create the form (I43/I21), add the personal-info block (I47), form options (I57), link a question to activities (I50), and maybe "add one question with its choices list".
- Opening `campaign.survey` writes data: it creates the Survey row and calls `enableIfReady`, which can put a non-registration campaign online (SurveryFormPage.php:39/:43). "Voir le formulaire" writes a demo Order row each time.
- Minors' data in this area: SetupFormStep decides collection of birth date, school, level and file number. The invitation import writes children's names (I7, upload). The students tab edits and deletes children's records. Change-course moves a child between groups. The map's AI analysis sends per-school counts and average declared grade to the AI provider (InscriptionMapAnalysisModal.php:95-110).
- Installment plans (org.settings/org.policies) are `auth`-only with no role check, and `InstallmentPlanForm` needs no extraction (simple `rules()`). Stop and resend-link are gated by `canBeManagedBy` (root team for multi-centre baskets). All three are small, high-value tasks: `money` for plans and stop, `outward` for resend.
- Already done or reusable: creating a registration campaign (I1) is in CreateCampaignTask, and sports receipts (I42) use `receiptsRules` in CampaignSettingsWriter. Audience (I2) reuses `StepCampaignDates::datesRules` plus the trait's `audienceRules`. Go-live (I5) is `CampaignGoLiveService::goLive`. Invitations (I9) are `InscriptionSetup::prepareInvitationCommunication` plus `CommunicationSender::send`, which re-mails everyone each time.
- Network pages (I37-I40) are the only inscription writes with a real server-side role gate: `NetworkCatalogCard::authorizeBoot` allows manager or agent on a parent team. Their rules are small, so they are easy tasks, and all are `outward` (slug changes break shared links).

#### Area notes

- Kompo AJAX writes go to `/_kompo` (vendor/kompo/kompo/routes/web.php), which has only the `web` middleware. The route groups (web.php:275 profile, web.php:385 manager, cms/teams `auth`) apply only when the page loads. Server-side guards are what each komponent's created()/authorize() checks. Examples: CampaignPageRecipients' isEditor check (CampaignPageRecipients.php:17) does not cover its child tables' selfPost methods, and the Communications and SMS pages have no role check at all (Members see both links).
- Many write methods load records by an id from the client with no team or campaign check: Recipient (disable, share profits, resend, edit form), Group (toggles, delete form), Communication (toggle, copy), SmsSending, Donor (unsubscribe), Customer (merge second id), MailingList/Page (edit by URL id). Only deletes routed through _DeleteLink check a policy or deletable(), and Customer::deletable and Page::deletable have no team check either. A Coco task must scope every id to currentTeamId()/currentCampaignId() itself.
- "Participant added" e-mails: CampaignListForm afterSave → Campaign::sendCommunicationsFor (Campaign.php:2416) sends every SEND_AFTER_ADD_PARTICIPANT communication **without checking `enabled`**. It only skips ended campaigns. It fires only for manual non-P2P adds (and for self-registration through sendSingleAfterRegisterCommunication). Excel, internal-list and GPI imports send nothing. No Recipient observer or event exists.
- The AI sequence creates new e-mails **enabled** (ExecuteCommunicationPlanJob.php:145, deliberate per its comment). That contradicts the help article ("tous arrivent désactivés"), and the article or the code needs fixing. Copy-from-campaign and duplicate keep the source's `enabled` too, so the arming of scheduled sends is immediate.
- Campaign leaders get no account and no invitation e-mail: they are only a recipient list. Group delegates and P2P captains are stored as Donor rows, also with no e-mail on save.
- Good reusable services for tasks: P2pService::upsertP2PRecipient (validated, transactional), CommunicationSender (send with 3-day cooldown, test), P2PParticipantsMessenger, SaveRecipientSetting, Group::createOrGetFromNames, Recipient::copyToCampaign, GricsSyncService, Customer::mergeWithCustomer, ImportRowCustomersImport::makeValidator (static), ExecuteCommunicationPlanJob. The rest have their rules inside rules() and would need static extraction, as CampaignSettingsWriter did.
- Best "yes" candidates (one draft → one write): add or edit a participant (R3/R4/R5; parent e-mails as a list field, MINORS), create a group or bulk groups (R25/R26), campaign leader (R13), registration page message (R19), create or edit a communication (R30, outward) plus schedule (R38), the no-sale reminder send (R24), and contact list criteria (R57).
- Destructive replace flows are not transactional. The participant Excel replace deletes partially when a paid participant aborts the loop (RecipientsImportErrorsQuery.php:156). The contacts Excel replace deletes all contacts before validating rows (CustomersImportErrorsQuery.php:142). The internal-list replace mass-deletes rows and bypasses Recipient::delete cleanup (RecipientsImportListModal.php:33).
- Participant Excel persist never re-validates rows server-side (RecipientsImportErrorsQuery.php:147), while the contacts import does (CustomersImportErrorsQuery.php:131).
- Outward sends to arbitrary addresses: the campaign test send (R40) puts a real, possibly minor, participant's personalised e-mail (with signed dashboard link) to any typed address. Newsletter tests and SMS tests also go to any address or number. A newsletter with no contact list goes to ALL contacts even when a campaign is chosen.
- Opening the newsletter-unsubscribe or donor-unsubscribe modal on a contact page writes the unsubscribe immediately in created(), before any save (UnsubscribeCustomerPage.php:25, UnsubscribePage.php:22).
- Read-only (no rows): P2P status/payment filters, ambassadors list, related links and dashboard links, group invitation links, send stats ("Voir"), exports. Group and participant goals, leaderboard, P2P settings, fees, tiers and challenges are settings cards (settings area). "Lier à" on an order belongs to the orders area.

#### Area notes

- **Server-side checks are thin.** `org.*` routes (`routes/kompo/teams.php:5`) have only `auth`, and `my-campaign/*` / event-night routes (`web.php:275`) have no role check. The only guards are the sidebar (`DashboardSidebar.php:371`) and `isManager()` UI hiding. Only member management (TeamPolicy), the network requests cards, manual payment (`CampaignOrderingTrait.php:156`) and refund/link (`OrderPolicy.php:63-75`) enforce a role in code.
- **Many write methods load records by an id the client sends, with no team or campaign check.** Affected: invitations, `saveForceApproval`, `InviteToBecomeOwnerModal`, tax receipts send/cancel/edit/create, mark delivered, change dates, replace product, scanner/terminal block, encan pledges/bids, entity linking, accounting accounts, membership cancel, webhook secret. A Coco task must load each record through `currentTeamId()` / `currentCampaign()` itself, not reuse these methods as they are.
- **Security findings to fix before exposing anything:**
  - `RoleManagementModal` accepts any `role`, including `admin` (rules :100). `admin` reaches `users.current_role`, so the member becomes a platform admin through `isAdmin()`.
  - `qr-code-check` (`web.php:62`) has no middleware. It marks tickets scanned and returns the buyer's e-mail. Revoking a scanner (`DashboardScannerUsersQuery.php:102`) does not invalidate anything.
  - The "let managers manage bank account" toggle has no owner check.
  - `InviteToBecomeOwnerModal` takes a team id from the payload. An existing account becomes owner at once.
- **Tax receipts have no validation and destroy data quietly.** `TaxReceiptForm` has empty rules: the admissible amount can exceed the payment, and nothing is audited. Re-creating a receipt (one order or "all donors") deletes the existing receipt and issues a new number with no cancellation notice (`TaxReceipt.php:213`). A tax-receipt task needs new rules and an explicit legal acknowledgement.
- **Code and help articles disagree in 3 places:**
  - "Renvoyer le reçu" re-sends the existing tax receipt and does not regenerate it (`regenerate:false`, `OrderReceiptsTrait.php:64`).
  - "Tirer ce prix" sends no e-mail to the winner (`DrawPrizeModal`). Only "Tirer tous les prix" e-mails, and it re-sends to every draw of the date.
  - Approving a campaign from the "Demandes" card sends no e-mail to the requester. Only the signed approval-request page does.
- **Raffle draws run in `created()` on a GET** (`DrawPrizeModal`, `DrawAllPrizesModal`). Draw-all uses `prize.quantity`, not the remaining quantity, so running it again duplicates winners. The encan individual charge is also a `selfGet`. Keep draws and encan charges out of Coco: they are `iterative`/`provider`.
- **`MultipleManualPaymentsModal` creates PAID orders that skip the normal payment completion** (no receipts, no tax receipts, no audit). Its `effective_date` can be in the future, and any team role can run it. Single manual payment (O55) uses the normal path but needs the public-page cart.
- **Good first tasks** (one record, simple rules, reversible or internal): advanced options (O14), analytics (O13), report e-mails (O12), tax display (O11), entity (O18), installment plan (O19), mark delivered (O51), change purchase date (O52), block terminal (O89), scanning date (O63), invite member (O2, rules already in `invitationRules()`). Each needs its `rules()` extracted as statics, the same way `CampaignSettingsWriter` does it.
- **Outward tasks with existing services:**
  - `ResendOrderEmail` rules (:44) cover receipt, ticket and draw-ticket resends.
  - `Team::inviteUser` covers invitations, but it adds an existing account with no consent and no e-mail.
  - `TaxReceipt::sendTheEmail` / `cancelReceipt` cover tax receipts.
  - `CampaignScannerInvitationsTrait` covers scanner invites. Its links never expire and are shared by every volunteer.
  - `Campaign::sendEncanPaymentRequest` covers encan payment requests.
- **Side effects nobody would expect:**
  - Opening the internal unsubscribe form unsubscribes the contact (`UnsubscribeCustomerPage.php:26`).
  - Saving a webhook rotates its secret (`WebhookForm.php:17`).
  - `CustomerForm::beforeSave` sets `team_id` to the current team even when editing.
  - Approving an access request grants Administrateur (manager) and overwrites the user's name (`User.php:690`).
- **Personal data:** participant-linked actions touch minors' names and family e-mails: link to participant (O54), multiple manual payments (O56), entities (O72) and delivery slips (O93). Buyer PII is written by O49 and O50 and by manual payments (O55, also sent to Stripe). The scan endpoint (O66) exposes buyer e-mails without login.

#### Area notes

- **No role check on any supplier write.** `role:supplier` (RoleMiddleware.php:27) only checks that the current team is a supplier, and it runs only on page GETs. Kompo actions go through `_kompo` with `web` middleware only. Membre and scanner users of a supplier team can change prices, payment settings, integrations and deliveries. Only the team-member forms (TeamPolicy addTeamMember = owner) and onboarding wording (authorizeBoot) check anything. A Coco task should gate these writes on isManager or above.
- **IDOR pattern: ids from the client payload are not checked against the supplier.** SupplierDeliverablesQuery.php:118 (product form, and beforeSave then sets supplier_id to the caller), discounts and rebates (deliverable_id prop), variants (AbstractVariantForm.php:15), deliveries (SupplierDeliveriesQuery.php:321, DashboardDeliveriesTable.php:98 → AcceptDeliveryModal), and invitations (SupplierTeamTable.php:144/149). Only Kompo deletes go through `deletable()`, which does check ownership. Any task must scope by `currentSupplier()` itself. Exploitability is OPEN.
- **Supplier writes that hit live client campaigns:**
  - stock (F4, F19) and season (F5), read at purchase;
  - $ volume discounts (F10/F11), read at campaign end in Campaign.php:829;
  - delivery conditions `pct_fee_to_org_for_delivery_to_customer` and customer delivery fees (F22);
  - delivery instructions e-mailed at each campaign start (F23);
  - onboarding wording and logo (F50/F51);
  - product delete (F8), which deletes copies from client campaigns.

  Name, description, images, cost, suggested price and hidden flag are copied once and never pushed to existing copies.
- **Payment tab bug (F24):** `SupplierPaymentSettingsForm::afterSave` (:15) calls `Supplier::updatePayFixedFees(null)` on every save made outside impersonation. That wipes `pay_fixed_fees` on the supplier and on every campaign with its `supplier_id`, live client copies included. Fix it before wrapping F24 in a task.
- **Delivery actions have no server-side state machine.** `acceptDelivery`, `markDeliveryComplete` and the fees `handle()` don't check `del_status` or stage. Only the button shown (AcceptDeliveryModal.php:221) enforces order, and there is no DB transaction. `markDeliveryComplete` creates the invoice and payout (BillCalculator → BillItem::createRelatedTransfer), with no undo. A task needs explicit guards plus money acknowledgement.
- **Unused or misleading paths:**
  - % rebates (F12) are shown to organisations but never applied to an invoice (AddDeliverableModal.php:52).
  - `SupplierShopifyForm` (link products, sync, disconnect) is not referenced anywhere. Shopify is connected only from Shopify (OAuth) and kept in sync by webhooks.
  - `SupplierInfoForm` validates `logo`, but the field is `profile_logo`.
- **Credentials:** `suppliers.shipstation_password` is a bcrypt hash generated by Coolecto (SupplierShipstationForm.php:38), and the plain value is shown once on screen. Machool keys use the `encrypted` cast (Supplier.php:46-47). Both are UI-entered per-supplier credentials stored in the table, which is the CLAUDE.md exception. Never echo them through Coco.
- **Shopify login surprise:** ShopifyController.php:47-56 logs the browser in as the supplier's user when the Shopify shop e-mail equals the supplier e-mail and nobody is authenticated. This is out of scope for tasks but worth a security review.
